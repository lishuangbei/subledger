# algo-switch：单一 Alpaca 实盘账户的多策略子账户方案

**问题**：一个 real-money Alpaca 账户，多个策略混用，资金/收益/额度无法分开追踪。

**目标**：一个 router，一端接 Alpaca（以后接 IB），另一端接多个策略/子账户；
每个子账户有独立资金上限、保证金额度；定时核对子账户总和与真实账户是否一致。

本仓库按要求做了两个实现，供对比 review：

```
option1-lumibot/   基于开源框架 Lumibot：多策略共享一个 broker 连接 + 自补的对账脚本
subledger/    自研 subledger：完整的虚拟子账户路由器（零依赖核心 + 22 个测试）
```

## 调研摘要（先看有没有现成的）

- **Alpaca 官方 OmniSub / Broker API**：真·sub-account，但要签机构合作协议，个人用不了。
- **Lumibot**（选为方案一基座）：唯一支持"一个账户连接 + 多策略 + 每策略 budget"
  且同时支持 Alpaca 和 IB 的成熟开源框架。
- **NautilusTrader**：架构最理想，但 Alpaca adapter 还在 RFC，暂不可用（值得长期关注，
  等 adapter 落地后是方案一的升级方向）。
- **LEAN / OpenAlgo**：分别因"单实例单算法/部署重"和"仅印度券商"排除。
- 没有找到任何现成开源项目直接做"个人账户虚拟 sub-account + 硬性资金隔离 + 对账"
  这件事 —— 这正是方案二自研的理由。

## 两方案对比

| 维度 | 方案一 Lumibot | 方案二 自研 subledger |
|---|---|---|
| 上手成本 | 低：装包、写策略类、run_all() | 中：自己维护一套 router 服务 |
| 策略开发 | 必须用 lumibot 的 Strategy 框架（但换来免费的回测能力） | 策略完全自由（任何语言/框架，REST 下单即可） |
| 资金隔离强度 | 软约束：budget + mixin 拦截，可被绕过 | 硬约束：router 是唯一持有 API key 的进程，策略拿不到真实账户 |
| 卖出隔离（A 不能卖 B 的持仓） | mixin 尽力拦截；进程重启后归属恢复不可靠 | 账本级保证，SQLite 持久化，重启无损 |
| 订单归属审计 | 无（策略快照粒度） | 每单 client_order_id 编码子账户，外来订单可检出 |
| 对账 | 快照总和 vs 账户，15 分钟 cron | 现金+持仓+外来订单三重核对，可自动拉闸（halt_on_drift） |
| 风控 | 无内建 | 单笔上限/当日止损/白名单/保证金倍数/kill switch |
| 保证金建模 | 无 | 简化倍数模型（真实兜底仍在券商侧） |
| 回测 | ✅ lumibot 内建 | ❌ 无（纯执行层，可与任何回测框架并存） |
| 接 IB | 官方支持，换一行 | 实现 5 个方法的 IBBroker adapter |
| 维护负担 | 跟随上游（API 偶有 breaking change） | 全部自己维护（核心 ~1200 行，零依赖） |
| 测试 | 依赖上游质量 | 22 个单测 + demo，`python3 -m unittest discover tests` 零依赖可跑 |

## 我的推荐

**两个方案其实是互补的，不是二选一：**

- 如果你的策略本来就想用 Python 写、想要免费回测，且能接受"纪律性隔离"
  （靠 mixin 约定而非硬性权限），方案一最省事。
- 如果你在意的是**记账正确性、策略间硬隔离、审计和对账**（你列的需求更偏这个），
  方案二是为这些需求量身做的：策略侧完全自由，router 层集中管控。
  它刻意做成纯执行层——你甚至可以**用 lumibot 回测、用 subledger 实盘执行**。

建议路径：先在 Alpaca **纸盘**（paper）把方案二跑一到两周（`ALPACA_PAPER=true`），
观察对账报告有没有意外 drift（费用、碎股、分红都会现形），确认后再切实盘。

## 快速验证（现在就能跑，无需任何凭据）

```bash
cd subledger
python3 -m unittest discover tests   # 22 tests
python3 examples/demo.py             # 端到端演示：隔离、风控、对账、drift 检测
```

## 已知风险（两个方案共同的、来自问题本身的）

1. **同一 symbol 多策略共持**：券商侧永远是净头寸。两方案都在账本层分账、按净额对账；
   但若一个策略做多另一个做空同一只票，券商侧会互相抵消（省保证金，但报表要靠账本）。
2. **洗售（wash sale）跨策略传染**：税务上 IRS 按账户看，A 策略卖亏、B 策略 30 天内
   买回同一只票会触发 wash sale——这是单账户多策略的固有税务问题，任何 router 都解决不了，
   选票池尽量不重叠可规避。
3. **PDT 规则**：账户 < $25k 时，所有策略的 day trade 次数是合并计算的。
4. **外部变动**（入金、分红、拆股、费用）都会表现为 drift——对账器负责发现，
   人（或 `absorb_cash_drift`）负责确认吸收。
